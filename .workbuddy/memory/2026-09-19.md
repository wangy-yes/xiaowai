## service/start.ps1（PowerShell 启动器）
- 为 `service/` 写了一个纯 PowerShell 版启动器 `start.ps1`，对齐原 `start.sh`：建 venv → 装 CPU torch 2.2.2 + 依赖 → 下模型(ASR ~900MB / 人脸 / Silero VAD) → 起主服务(:9000)，`-StartWeb` 额外开 :5050。
- 关键坑：**中文 Windows + PowerShell 5.1 读无 BOM 的 .ps1 会按 GBK 解码**，脚本里中文串的多字节被误读成 `"` 等字符 → 字符串提前闭合 → 解析报「意外的 }」。必须保存为 **UTF-8 带 BOM**。已用 `[System.IO.File]::WriteAllText($p, $c, [System.Text.UTF8Encoding]::new($true))` 强制写入 BOM，真机验证 `.\start.ps1` 可正常解析运行。
- Python 选择：本机 `py` launcher 有 3.12（默认 `*`）和 3.13（托管版，默认 `python`）；脚本默认锁 `py -3.12`，避开 3.13 无 torch 2.2.2 cp313 wheel 的坑。
- 真机冒烟测试（`-SkipSetup -SkipModelDownload`）通过：正确选 3.12、读 .env、缺模型优雅 exit 1。
- 注：本机 `ffmpeg` 已装(9.0.1)，无需额外装。

## webrtcvad 在 Windows/py3.12 装不上
- `pip install -r requirements.txt` 卡在 `webrtcvad==2.0.10`：PyPI 上该版只有老 Python(≤3.9) 预编译 wheel，py3.12 无 wheel → 现场编译需 MSVC → 失败。
- 修法：把 `service/requirements.txt` 第 8 行 `webrtcvad==2.0.10` 换成 `webrtcvad-wheels==2.0.14`（daanzu 的 fork，导入名仍是 `webrtcvad`，带 Windows x86_64 + cp312 现成 wheel）。已实测 `import webrtcvad` OK。
- 重跑 `.\start.ps1` 即可续装剩余依赖。注意：此改动偏离上游 requirements.txt，若以后 `git pull` 上游覆盖需重改（或在本机装 MSVC Build Tools 走原版）。

## 启动崩溃链排查（续）
- **opus 缺失**：`import opuslib_next` 在 Windows 启动即崩 `Could not find Opus library`。根因：`opuslib_next/api/__init__.py` 只靠 `ctypes.util.find_library("opus")`，而 **find_library 在 Windows 上永远返回 None**（不搜第三方 DLL），且它只给 macOS/Linux 写了兜底路径。修复：① 复用本机已有的 `C:\Users\wangyue\AppData\Local\OpenDeskBotV2\...\pyogg\opus.dll`（标准 libopus），复制到 `service/.venv/Scripts/opus.dll`；② 给该 `__init__.py` 补一段 Windows 兜底（显式搜 exe 目录/PATH/System32 的 `opus.dll`，再 `ctypes.CDLL("opus")` 兜底）。已实测 Decoder/Encoder 创建 OK。**注意**：此改动在 `site-packages`，`pip install -U opuslib_next` 会覆盖，需重打。
- **config.yaml 找不到**：`start.ps1` 启动 `deskbot_server` 时 CWD 是仓库根而非 `service/`，服务按 CWD 找 `config.yaml` 失败。修复：在 `start.ps1` 的 `$ROOT=$PSScriptRoot` 后加 `Set-Location $ROOT`。
- **ASR ONNX 导出 OOM 打挂服务**：`ensure_asr_quant_onnx` 只在 `import` 处 try/except，真正 `SenseVoiceSmall(quantize=True)` 导出那行没保护 → OOM 冒泡崩溃。`service/.../asr/model_dir.py` 已把导出调用包进 try/except（失败回退 PyTorch）。另把 `config.yaml` 的 `use_quant_onnx` 改为 `false`，直接走 PyTorch，避免每次启动撞量化导出的内存峰值。
- **当前最终拦路石 = 物理内存**：`models/SenseVoiceSmall/model.pt` 是 892MB FP32 权重，加载进内存峰值 ~1.2GB+。本机在加载模型时被系统直接杀进程（无 Python 栈、退出码 0），连一次性导出量化 ONNX 也 OOM。这是纯内存容量问题，**代码层面无解**：`torch.load` 用 mmap 也救不了（funasr 还会 `copy.deepcopy` + `load_state_dict`，FP32 权重必实驻内存）。
- 解决方向（需 sir 在真机操作）：① 关掉占用大内存的软件后重试；② Windows 加大页面文件（虚拟内存）到 8~16GB，提升提交上限，torch 的 CPU 分配器就能要到内存；③ 内存够后重新 `.\start.ps1` 即可起（opus/config/ONNX 均已修）；若想走轻量路径，内存宽裕时跑一次 `from funasr_onnx import SenseVoiceSmall; SenseVoiceSmall(model_dir, quantize=True)` 生成 `model_quant.onnx`，再把 `use_quant_onnx` 改回 `true`。
